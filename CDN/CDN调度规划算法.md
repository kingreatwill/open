# CDN 调度规划算法

## 1. 文档目标

本文描述 CDN 调度规划系统如何根据未来流量、节点容量、网络质量、带宽成本和容灾要求，提前生成区域到 CDN 节点的流量分配计划。

规划系统输出的不是单个请求的实时路由结果，而是未来一段时间的目标流量比例，例如：

```text
规划时间：20:00—20:05

北京电信：
  北京节点 A：55%
  天津节点 B：30%
  济南节点 C：15%

上海移动：
  上海节点 D：70%
  杭州节点 E：30%
```

实时调度系统根据这个目标比例分配流量，并在节点故障、突发过载或网络质量恶化时执行快速兜底。

## 2. 规划系统与实时调度的边界

| 模块 | 典型周期 | 主要职责 |
|---|---:|---|
| 容量规划 | 天、周、月 | 节点建设、扩容、带宽采购、长期成本优化 |
| 流量调度规划 | 5—30 分钟 | 预测流量并生成区域到节点的目标分配比例 |
| 实时调度 | 秒级或请求级 | 执行目标权重，处理故障、过载和突发流量 |
| 健康检查 | 1—10 秒 | 探测节点、线路和服务可用性 |

规划算法负责全局优化，实时调度负责快速反应。二者必须分层，不能用离线规划代替故障切换，也不应让实时系统承担复杂的全局成本优化。

## 3. 输入与输出

### 3.1 输入数据

规划系统至少需要以下数据：

1. 用户区域：国家、省份、城市、运营商、ASN 或 IP 段。
2. 预测流量：每个区域、业务和时间片的带宽或请求量。
3. 节点容量：出口带宽、连接数、CPU、存储和服务容量。
4. 网络质量：RTT、丢包率、建连时间、成功率和历史稳定性。
5. 调度关系：某个区域是否允许调度到某个节点。
6. 成本数据：带宽单价、95 峰值费用、跨运营商费用和云出口费用。
7. 节点状态：健康、维护、限流、扩容、降级和禁用状态。
8. 历史计划：上一周期的分配比例，用于限制调度震荡。

### 3.2 输出数据

规划结果通常包含：

```json
{
  "time_slot": "2026-08-05T20:00:00+08:00",
  "region": "CN-BJ-TELECOM",
  "predicted_gbps": 100,
  "allocations": [
    {"node": "bj-a", "traffic_gbps": 55, "weight": 55},
    {"node": "tj-b", "traffic_gbps": 30, "weight": 30},
    {"node": "jn-c", "traffic_gbps": 15, "weight": 15}
  ],
  "fallback_nodes": ["sjz-d"],
  "plan_version": 1024
}
```

## 4. 数学模型

### 4.1 变量定义

- \(u\)：用户区域，可以是省份、运营商、ASN 或 IP 段。
- \(n\)：CDN 节点。
- \(t\)：规划时间片。
- \(d_{u,t}\)：区域 \(u\) 在时间片 \(t\) 的预测流量。
- \(C_{n,t}\)：节点 \(n\) 在时间片 \(t\) 的可用容量。
- \(x_{u,n,t}\)：区域 \(u\) 分配给节点 \(n\) 的流量。
- \(a_{u,n}\)：区域 \(u\) 是否允许调度到节点 \(n\)。
- \(q_{u,n,t}\)：区域到节点的网络质量代价。
- \(c_{n,t}\)：节点的单位流量成本。
- \(x^{old}_{u,n,t}\)：上一版计划中的分配流量。

其中：

\[
a_{u,n} \in \{0,1\},\qquad x_{u,n,t}\ge 0
\]

### 4.2 流量守恒

每个区域的预测流量必须全部分配：

\[
\sum_n x_{u,n,t}=d_{u,t}
\]

如果允许少量流量进入兜底池，可以引入缺口变量 \(s_{u,t}\)：

\[
\sum_n x_{u,n,t}+s_{u,t}=d_{u,t}
\]

并对 \(s_{u,t}\) 设置很高的惩罚，保证只有在容量确实不足时才使用兜底。

### 4.3 节点容量约束

\[
\sum_u x_{u,n,t}\le C_{n,t}\rho_n
\]

其中 \(\rho_n\) 是安全利用率，一般设置为 0.75—0.90。例如节点容量为 100 Gbps，安全利用率为 0.85，则规划最多分配 85 Gbps。

### 4.4 线路可达性约束

\[
x_{u,n,t}\le a_{u,n}M
\]

\(M\) 是足够大的常数。如果节点不允许服务该区域，则 \(a_{u,n}=0\)，对应分配流量必须为零。

### 4.5 网络质量约束

网络质量可以作为硬约束：

```text
RTT > 80 ms       → 禁止调度
丢包率 > 3%       → 禁止调度
建连成功率 < 99%  → 禁止调度
```

也可以在满足基本 SLA 后，将质量差异放入目标函数进行优化。

### 4.6 单节点比例约束

为了降低单节点故障影响：

\[
x_{u,n,t}\le d_{u,t}r_{max}
\]

例如 \(r_{max}=0.7\)，表示单个节点最多承载某区域 70% 的流量。

### 4.7 调度变化约束

限制相邻计划之间的变化量：

\[
|x_{u,n,t}-x^{old}_{u,n,t}|\le \Delta_{u,n,t}
\]

生产环境中一般限制单次权重变化不超过 10%—20%。故障节点可以绕过此限制并立即摘除。

### 4.8 最小分配约束

如果节点一旦进入调度池就必须获得有意义的流量，可以使用二进制变量 \(y_{u,n,t}\)：

\[
y_{u,n,t}\in\{0,1\}
\]

\[
x_{u,n,t}\ge y_{u,n,t}x_{min}
\]

\[
x_{u,n,t}\le y_{u,n,t}x_{max}
\]

这可以避免大量只有 0.1% 权重、实际难以观测和控制的节点。

## 5. 目标函数

一个可落地的多目标函数为：

\[
\min \left(
0.35Q+0.30B+0.20R+0.15S
\right)
\]

其中：

- \(Q\)：网络质量成本。
- \(B\)：带宽和线路成本。
- \(R\)：过载与故障风险。
- \(S\)：计划变更成本。

### 5.1 网络质量成本

\[
Q=\sum_{u,n,t}x_{u,n,t}q_{u,n,t}
\]

质量代价可以通过归一化指标计算：

\[
q=0.5RTT_{norm}+0.3Loss_{norm}+0.2ConnectTime_{norm}
\]

### 5.2 带宽成本

\[
B=\sum_{u,n,t}x_{u,n,t}c_{n,t}
\]

如果使用 95 峰值计费，需要额外估算本次流量是否会抬高计费峰值，不能简单使用固定单价。

### 5.3 过载风险

节点利用率越接近容量上限，惩罚应当越快增长：

\[
R_n=\left(\frac{load_n}{capacity_n}\right)^4
\]

该函数使 60% 到 70% 的变化惩罚较小，而 85% 到 95% 的变化惩罚明显增大。

### 5.4 计划变更成本

\[
S=\sum_{u,n,t}|x_{u,n,t}-x^{old}_{u,n,t}|
\]

变更成本能够避免节点评分轻微波动就引起大规模流量迁移。

## 6. 常用规划算法

### 6.1 线性规划 LP

当流量可以连续拆分、所有约束都是线性关系时，优先使用线性规划。

典型模型：

\[
\min \sum_{u,n,t}x_{u,n,t}(\alpha q_{u,n,t}+\beta c_{n,t})
\]

适用场景：

- 生成区域到节点的流量比例。
- 节点容量和网络质量约束明确。
- 需要全局最优且结果可解释。

常用求解器包括 OR-Tools、HiGHS、Gurobi、CPLEX 和 SCIP。

### 6.2 混合整数规划 MILP

当规划包含节点启停、线路选择、内容预热或容量采购等离散决策时，使用 MILP。

定义节点启用变量：

\[
y_{n,t}\in\{0,1\}
\]

容量约束变为：

\[
\sum_u x_{u,n,t}\le C_{n,t}y_{n,t}
\]

MILP 适合节点建设、扩容、云资源开关和缓存部署规划，但大规模问题的求解时间通常高于 LP。

### 6.3 最小费用最大流

单时间片的 CDN 流量规划可以转换成网络流：

```text
源点 → 用户区域 → CDN 节点 → 汇点
```

- 源点到区域的容量是区域需求。
- 区域到节点的容量是线路允许流量。
- 区域到节点的费用是质量成本与带宽成本。
- 节点到汇点的容量是节点安全容量。

当约束结构比较简单时，最小费用流通常比通用 LP 更快。

### 6.4 多商品流

如果需要规划边缘节点、区域中心、骨干链路和源站之间的多级路径，可以使用多商品流模型：

```text
用户 → 边缘节点 → 区域中心 → 源站
```

不同区域、租户或业务是不同商品，共享骨干链路容量：

\[
\sum_k flow_{k,e}\le capacity_e
\]

该算法适合 CDN 内部流量工程和回源路径规划。

### 6.5 贪心算法

当问题规模很大，或者需要秒级生成可行计划时，可以使用贪心算法：

1. 按区域预测流量从大到小排序。
2. 过滤不可用节点。
3. 计算每个候选节点的增量成本。
4. 优先向增量成本最低的节点分配流量。
5. 节点达到安全容量后继续选择下一个节点。
6. 对最终计划执行过载修复、权重取整和平滑。

增量成本可以定义为：

\[
cost_{u,n}=0.4NetworkCost+0.3LoadCost+0.2BandwidthCost+0.1ChangeCost
\]

贪心算法容易实现且速度快，但不能保证全局最优，适合用作优化求解失败时的兜底方案。

### 6.6 拉格朗日松弛与分解

当问题达到几十万 IP 段、数千节点和大量时间片时，可以按区域、运营商或业务拆分，再通过节点容量价格协调。

调整后的节点成本为：

\[
adjustedCost_{u,n}=baseCost_{u,n}+\lambda_n
\]

节点过载时提高影子价格：

\[
\lambda_n^{k+1}=\max(0,\lambda_n^k+\eta(load_n-capacity_n))
\]

各子问题会逐渐减少对紧张节点的使用，最终收敛到全局可行方案附近。

### 6.7 鲁棒优化

流量预测存在误差，可以使用需求区间：

\[
d_{u,t}\in[\hat d_{u,t}-\epsilon,\hat d_{u,t}+\epsilon]
\]

工程上常用的简化方式是：

\[
planningDemand=\hat d+k\sigma
\]

- \(\hat d\)：预测均值。
- \(\sigma\)：历史预测误差标准差。
- \(k\)：风险系数。

例如预测流量为 80 Gbps，误差标准差为 8 Gbps，\(k=1.5\)，则按照 92 Gbps 进行容量规划。

### 6.8 随机规划

如果可以构造正常流量、热点流量、节点故障等多种场景及其概率，可以最小化期望成本：

\[
\min \sum_s p_sCost(x,s)
\]

对极端风险要求较高时，可以增加 CVaR：

\[
\min ExpectedCost+\lambda CVaR
\]

随机规划比鲁棒余量更加精细，但数据准备和求解成本也更高。

## 7. 推荐的生产方案

推荐采用“预测 + 候选过滤 + LP/最小费用流 + 结果修复 + 滚动执行”的分层方案。

### 7.1 第一阶段：流量预测

按以下粒度预测未来 30—120 分钟流量：

```text
区域 × 运营商 × 业务 × 时间片
```

除点预测外，还应输出误差区间或分位数，例如 P50、P90 和 P99。

### 7.2 第二阶段：候选节点过滤

在进入优化器之前执行硬过滤：

```text
健康检查失败       → 排除
节点处于维护状态   → 排除
ISP 或 ASN 不匹配   → 排除
RTT 超过硬 SLA      → 排除
丢包率超过阈值     → 排除
不支持目标协议     → 排除
容量利用率超过 90% → 停止调入
```

硬过滤用于保证安全，优化评分不能覆盖硬约束。

### 7.3 第三阶段：生成基础计划

优先采用 LP 或最小费用流生成全局基础计划：

```text
目标：质量、成本、风险和稳定性综合最优
约束：容量、线路、SLA、冗余和变化幅度
```

如果在规定时间内未获得可行解，则降级到贪心算法。

### 7.4 第四阶段：计划修复

求解器输出需要经过工程化修复：

1. 删除低于最小权重的节点。
2. 将连续流量转换成整数权重。
3. 修正取整造成的比例误差。
4. 再次检查节点容量。
5. 补充主备和区域兜底节点。
6. 限制与上一版计划的变化幅度。

### 7.5 第五阶段：滚动时域执行

采用模型预测控制 MPC：

```text
每 5 分钟运行一次
预测未来 60 分钟
生成未来 60 分钟计划
只执行最前面的 5 分钟
下一周期根据真实数据重新规划
```

滚动规划能够持续修正预测误差，并减少一次性长周期计划失效的风险。

### 7.6 第六阶段：灰度与流量爬坡

不要一次性将旧计划切换为新计划。例如：

```text
旧计划：A=80，B=20
新计划：A=40，B=60
```

可以分阶段下发：

```text
第 1 轮：A=70，B=30
第 2 轮：A=60，B=40
第 3 轮：A=50，B=50
第 4 轮：A=40，B=60
```

故障摘除不需要爬坡，节点恢复和新节点上线必须从小流量开始。

## 8. 推荐算法伪代码

```text
function BuildPlan(currentTime):
    horizon = [currentTime, currentTime + 60min]
    demand = ForecastTraffic(horizon)
    capacity = LoadNodeCapacity(horizon)
    quality = LoadNetworkQuality(horizon)
    previousPlan = LoadPreviousPlan()

    candidates = BuildCandidateGraph()
    candidates = FilterUnhealthyNodes(candidates)
    candidates = FilterByISPAndASN(candidates)
    candidates = FilterByHardSLA(candidates, quality)

    demand = AddForecastSafetyMargin(demand)

    plan = SolveLinearProgram(
        demand,
        capacity,
        quality,
        candidates,
        previousPlan
    )

    if plan has no feasible solution:
        plan = SolveByGreedyFallback(...)

    plan = RemoveTinyAllocations(plan)
    plan = ConvertToIntegerWeights(plan)
    plan = RepairCapacityViolations(plan)
    plan = AddFallbackNodes(plan)
    plan = LimitWeightChanges(plan, previousPlan)

    if ValidatePlan(plan) fails:
        return KeepPreviousSafePlan()

    PublishPlanCanary(plan)
    return plan
```

## 9. 调度权重转换示例

规划器得到：

```text
北京电信预测流量：100 Gbps

北京节点 A：55 Gbps
天津节点 B：30 Gbps
济南节点 C：15 Gbps
```

转换成百分比权重：

```text
A = 55
B = 30
C = 15
```

如果调度系统只支持较小整数，可以约简为：

```text
A = 11
B = 6
C = 3
```

权重下发后需要根据实际流量反馈校准，因为 DNS 缓存、递归解析器聚合和客户端连接复用都会导致实际比例偏离目标比例。

## 10. 故障和过载处理

### 10.1 规划失败

处理顺序建议为：

1. 放宽软质量目标。
2. 启用区域兜底节点。
3. 启用全国兜底节点。
4. 使用上一版安全计划。
5. 告警容量不足，不得静默生成超容量计划。

### 10.2 节点过载

建议设置分级阈值：

```text
利用率 < 75%：正常调入
75%—85%：降低新增权重
85%—90%：停止增加流量
> 90%：主动迁出流量
```

### 10.3 节点恢复

节点恢复应满足：

```text
连续多次健康检查成功
网络质量稳定
容量指标正常
完成 1%—5% 的小流量验证
```

恢复和摘除使用不同阈值，形成滞回，避免节点反复加入和退出调度池。

## 11. 参数建议

| 参数 | 建议值 |
|---|---:|
| 规划周期 | 5—10 分钟 |
| 预测窗口 | 30—120 分钟 |
| 计划执行窗口 | 5—10 分钟 |
| 节点安全利用率 | 75%—85% |
| 容量预留 | 15%—25% |
| 单节点最大区域占比 | 60%—70% |
| 单次权重变化上限 | 10%—20% |
| 新节点初始流量 | 1%—5% |
| 节点恢复观察期 | 1—5 分钟 |
| DNS TTL | 30—120 秒 |
| 优化器求解时限 | 5—30 秒 |

这些值需要根据业务流量规模、DNS 生效速度、节点数量和容灾等级进一步校准。

## 12. 评估指标

不能只评价求解器目标值，还需要持续观测计划执行效果。

### 12.1 质量指标

- 平均及 P95/P99 RTT。
- 丢包率。
- TCP/TLS/QUIC 建连成功率。
- HTTP 请求成功率。
- 首字节时间和下载速度。

### 12.2 容量指标

- 节点最大利用率。
- 超过 85% 利用率的节点数量。
- 容量不足时间和缺口流量。
- 各节点安全余量。

### 12.3 计划稳定性

- 每轮迁移流量比例。
- 节点权重变化次数。
- 节点反复摘除和恢复次数。
- 新旧计划差异。

### 12.4 成本指标

- 单位流量成本。
- 95 峰值带宽成本。
- 跨运营商和跨区域流量比例。
- 云出口和回源流量费用。

### 12.5 执行准确性

定义计划偏差：

\[
deviation_{u,n}=\frac{|actual_{u,n}-planned_{u,n}|}{planned_{u,n}}
\]

长期偏差较大的区域需要根据 DNS 缓存、解析器聚合和历史执行数据进行反馈校正。

## 13. 算法选择建议

| 场景 | 推荐算法 |
|---|---|
| 单时间片、约束简单、要求高性能 | 最小费用最大流 |
| 多时间片、连续流量比例优化 | 线性规划 LP |
| 节点启停、扩容、内容部署 | 混合整数规划 MILP |
| 多级 CDN 和骨干路径规划 | 多商品流 |
| 超大规模、需要快速获得可行解 | 贪心算法加修复 |
| 超大规模全局优化 | 分解算法或拉格朗日松弛 |
| 流量预测误差大 | 鲁棒优化 |
| 有明确故障和流量场景概率 | 随机规划或 CVaR |

## 14. 最终建议

大多数 CDN 调度规划系统可以从以下方案开始：

```text
短期流量预测
    + 候选节点硬过滤
    + 线性规划或最小费用流
    + 15%—25% 容量预留
    + 权重取整与变化限制
    + 5 分钟滚动重新规划
    + 贪心算法故障兜底
    + 在线实际流量反馈校准
```

核心原则是：

1. 用硬约束保证健康、容量、线路和 SLA 安全。
2. 用优化目标平衡网络质量、带宽成本和调度稳定性。
3. 用滚动规划修正预测误差。
4. 用容量预留和冗余节点应对突发流量。
5. 用灰度、爬坡和滞回机制避免调度震荡。
6. 规划系统生成目标比例，实时系统负责执行、故障切换和快速保护。
